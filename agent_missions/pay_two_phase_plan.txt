The Two Phases — Plain English
🟢  PHASE 1 — PRE-SHIFT
The number shown to staff before a shift happens.
• No actual work has happened yet
• No GPS data exists yet
• No paper timesheet exists yet
• This is a DISPLAY / INCENTIVE number only
• Changing it does NOT affect payroll
• 100% safe to fix immediately
KNOWN BUG: Staff Portal shows £300. Correct is £275. Marketplace already shows £275. Text messages already show £275. Label '12h worked' on a future shift is factually wrong — shift hasn't happened.
🔵  PHASE 2 — POST-SHIFT
The number used to actually pay staff.
• Shift has happened
• GPS clock data may exist
• Paper timesheet may have been uploaded
• Figures are DYNAMIC — based on actuals
• Any change here affects REAL payroll
CURRENT STATE: Pay calculation is working correctly. £300 never appears in approved timesheets. The previous double-deduction bug was fixed. Phase 2 tasks are about completing missing infrastructure paths (no-GPS fallback, OCR write-back, review matrix) and fixing misleading labels.
💡  Why '£300 vs £275' is ONLY a pre-shift problem
Post-shift, the system recalculates everything from actual GPS clock times. raw_total_hours (GPS) = 12. break_duration_minutes (client contract) = 60. total_hours = 12 − 1 = 11 payable. staff_pay_amount = 11 × £25 = £275. This recalculation already works correctly. Once a shift has been worked, you will NEVER see £300 in an approved timesheet — the £300 bug only lives in DRAFT (pre-shift) records. The Phase 1 fix is a one-formula change at timesheet creation time.

POINT 0  Context Brief — Read Before All Other Points
🔧 Reference — no action
⏱  Understand before executing any point
You are working on ACG StaffLink, a healthcare staff scheduling SaaS.
Database: Supabase project rzzxxkppkiasuouuglaf, eu-central-1, PostgreSQL 17.
Frontend: JavaScript/React.
THE CORE PROBLEM (pre-shift only):
Before a shift happens, staff are shown an expected pay amount. For a 12h shift at £25/hr
at a client with a 60-minute contracted break, the correct incentive figure is:
  £275  =  (12h − 1h break) × £25  =  11h × £25
Currently Staff Portal shows £300 (12 × £25 = gross, break not applied).
Marketplace already shows £275. Text messages already show £275.
CRITICAL RULE — TWO SEPARATE CONCEPTS:
  DURATION  =  shift.duration_hours  =  12h  NEVER changes.  Do not touch this.
  EXPECTED PAY  =  payable_hours × pay_rate  =  £275  This is what needs fixing.
CONTRACTED BREAK SOURCE:
  clients.contract_terms->>'break_duration_minutes'  (integer, 0 or 60)
  Also copied to: timesheets.break_duration_minutes  at timesheet creation
THE CANONICAL PAY FORMULA (use everywhere going forward):
  payable_hours = raw_hours >= 10 ? raw_hours − (break_mins / 60) : raw_hours
  staff_pay     = Math.round(payable_hours × pay_rate × 100) / 100
  client_charge = Math.round(payable_hours × charge_rate × 100) / 100
Phase 1 = pre-shift display fix. Phase 2 = post-shift infrastructure completions.
Post-shift pay calculation is already working correctly. No post-shift pay bug exists.
POINT 1.1  Backfill: Fix staff_pay_amount on all existing DRAFT timesheets
🔧 SQL Editor — Supabase
⏱  Execute now. 5 minutes. Zero payroll impact.
WHAT: 10 DRAFT timesheets store staff_pay_amount = £300 (gross). Correct is £275 (net after break).
The Staff Portal reads this field directly to display expected pay. Fixing the DB fixes the display
automatically — no frontend code change needed.
SCOPE GUARD (critical): Only touch records where ALL of these are true:
  status = 'draft'  AND  clock_in IS NULL  AND  financial_locked = false
  AND  break_duration_minutes = 60  AND  pay_rate IS NOT NULL
DO NOT TOUCH: Zero-break clients (£146.52 records) — these are correct.
DO NOT TOUCH: Records with clock_in populated — those are post-GPS, already correct.
EXPECTED OUTCOME: 10 rows updated from £300 → £275.
Run the verification query immediately after. All rows must return 'OK'.
📋  Instruction / SQL to execute:
-- STEP 1: Update
UPDATE timesheets
SET staff_pay_amount = ROUND(
  CASE WHEN total_hours >= 10
       THEN (total_hours - (break_duration_minutes::NUMERIC / 60)) * pay_rate
       ELSE total_hours * pay_rate
  END, 2)
WHERE status = 'draft'
  AND clock_in IS NULL
  AND financial_locked = false
  AND break_duration_minutes = 60
  AND pay_rate IS NOT NULL
  AND total_hours IS NOT NULL;
-- STEP 2: Verify (all rows must show 'OK')
SELECT id, shift_date, total_hours, break_duration_minutes, pay_rate,
       staff_pay_amount AS stored,
       ROUND((total_hours - break_duration_minutes/60.0) * pay_rate, 2) AS expected,
       CASE WHEN ABS(staff_pay_amount -
                    ROUND((total_hours - break_duration_minutes/60.0)*pay_rate,2)) < 0.01
            THEN 'OK' ELSE '⚠ MISMATCH' END AS check
FROM timesheets
WHERE status = 'draft' AND break_duration_minutes > 0 AND clock_in IS NULL
ORDER BY shift_date;

POINT 2.3  Build: No-GPS fallback — derive hours from OCR times when GPS unavailable
🔧 Code agent — needs codebase (OCR handler)
⏱  This sprint. 2-3 hours. Finance-critical missing path.
WHAT: When clock_in is null (no GPS) but OCR extraction succeeded, raw_total_hours is null.
The system has no actuals and cannot calculate pay. Build the fallback.
WHERE: In the OCR completion handler, after extractedData is available, add:
  if (timesheet.clock_in === null && extractedData?.rows?.[0]) {
    const ocrStart = extractedData.rows[0].start_time   // e.g. '08:00'
    const ocrEnd   = extractedData.rows[0].end_time     // e.g. '20:00'
    const ocrRawHours = parseFloat((
      (parseTime(ocrEnd) - parseTime(ocrStart)) / 60
    ).toFixed(2))
    const breakMins = timesheet.break_duration_minutes ?? 60
    const payable   = ocrRawHours >= 10 ? ocrRawHours - breakMins/60 : ocrRawHours
    await supabase.from('timesheets').update({
      raw_total_hours: ocrRawHours,
      total_hours: payable,
      staff_pay_amount: Math.round(payable * timesheet.pay_rate * 100) / 100,
      client_charge_amount: Math.round(payable * timesheet.charge_rate * 100) / 100,
      status: 'pending_admin_review',
      validation_notes: 'No GPS — hours derived from paper timesheet. Manual review required.'
    }).eq('id', timesheetId)
  }
CRITICAL: status MUST be set to pending_admin_review. Paper-only timesheets must
NEVER be auto-approved regardless of OCR confidence score. GPS is the only fraud-resistant source.
ACCEPTANCE TEST: Submit a timesheet for a shift with no GPS clock-in.
After OCR: raw_total_hours populated, staff_pay_amount calculated, status=pending_admin_review.
POINT 2.4  Build: Implement the mismatch review matrix in admin approval workflow
🔧 Code agent — needs codebase
⏱  This sprint. 3-4 hours. Finance-critical — ensures pay integrity.
WHAT: Build a function evaluateTimesheetForApproval(timesheet) that runs before any
timesheet moves to approved status. Enforce the decision matrix below.
THE MATRIX — implement each case:
CASE 1 — GPS present, paper matches GPS (within 0.5h tolerance):
  → autoApprove = true. Pay from GPS raw_total_hours. Status → approved.
CASE 2 — GPS present, paper OVERSTATES total by > 0.5h:
  → autoApprove = false. Status → pending_admin_review.
  → Pay on GPS hours (not paper). Admin 48h SLA to review.
  → Do NOT hold payment indefinitely.
CASE 3 — GPS present, paper understates by < 0.5h:
  → autoApprove = false. Status → pending_admin_review.
  → Pay on GPS hours. Flag as possible staff paper error.
CASE 4 — GPS present, actual hours < 10h (short shift — 10-hour rule):
  → No break deduction even if break_duration_minutes = 60.
  → payable_hours = raw_total_hours. Auto-approve eligible.
CASE 5 — No GPS, OCR available (from Point 2.3):
  → ALWAYS pending_admin_review. Never auto-approve.
CASE 6 — No GPS, no paper uploaded within 48h of shift end:
  → Create escalation notification. Set status = timesheet_overdue. Do not pay.
CASE 7 — OCR: supervisor signature absent (extracted_data.approval_stamp = false):
  → autoApprove = false. Notify staff. Admin review required.
ACCEPTANCE TEST: Test each case with a real or test timesheet. Each must route correctly.
